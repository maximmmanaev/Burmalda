## Задача

### 1. Добавить `BossRoomTileKind.Echo`

`Core/BossRoomTileKind.cs` — четвёртый элемент enum, doc-комментарий по
аналогии с соседними (PRD v8 §8.2: «×2 к текущему множителю, 1–3 на
комнату, в самых опасных точках»).

### 2. Двухуровневая математика в `RoomMultiplier`

PRD v8 §8.3 задаёт это не формулой «сумма аддитивов × произведение
множителей», а **последовательным применением операций в порядке, в
котором игрок берёт плиты** — проверь на двух примерах из PRD прямо в
тесте:

- `+0.5, +0.5, ×2` → `(1 → 1.5 → 2.0 → 4.0)` = **×4**
- `×2, +0.5, +0.5` → `(1 → 2.0 → 2.5 → 3.0)` = **×3**

Оба случая уже получаются, если добавить один новый метод
`ApplyEchoTile() => CurrentMultiplier *= EchoFactor;` (константа `2f`,
по аналогии с `ResonanceBonus`) — **не переделывай существующую
арифметику** `ApplyResonanceTile`/`TickRiftResonance`, она уже
последовательная (`+=` в порядке вызовов) и даёт правильный результат
без изменений, если методы вызываются в реальном хронологическом
порядке сбора плит. Главное — тест именно на порядок вызовов, не только
на конечное число, чтобы поймать регрессию, если кто-то потом
«оптимизирует» это в формулу.

### 3. `BossRoom.CollectEcho()`

По аналогии с `CollectVein`/`CollectResonance` в `BossRoom.cs` — вызывает
`Multiplier.ApplyEchoTile()`, с той же проверкой `if (!IsActive) return;`.

### 4. Интеграция с реальным забегом (сейчас `BossRoom` — сирота)

1. Точка входа: когда `GridTraceTrail` продвигается на плитку с
   `Tile.IsBoss` (см. `Boss/BossEncounterSystem.cs` — раньше здесь
   мгновенно резолвился старый Босс, по таблице миграции в roadmap это
   заменяется входом в Комнату) — создать `BossRoom` на реальные
   границы сегмента Комнаты (entryRow/exitRow), не выдумывая числа
   заново — параметры по Ярусу можно взять черновыми, баланс всё равно
   в Спринте 21.
2. Подписка на `GridTraceTrail.PositionChanged`/`Advanced` — по аналогии
   с тем, как `LeverActivationSystem` уже подписан (см.
   `Generation/LeverActivationSystem.cs` как образец паттерна): по
   пришедшей координате читать `Tile.BossRoomTile` и звать
   `CollectVein`/`CollectResonance`/`CollectEcho`/тикать `Rift`, пока
   стоишь на нём.
3. Тик волны и `ReportPlayerRow` — как `Decay.TrailDecaySystem.Tick`
   вызывается каждый кадр независимо от лока ввода (см. doc-комментарий
   `GridTraceInputController`) — `BossRoom.TickWave`/`TickWave`-подобный
   вызов должен работать по той же логике, распад/волна не
   останавливаются на примеривании.
4. Планировка самой Комнаты как сегмента: `SegmentTileType.Boss` уже
   есть как маркер входа (не трогать) — планировку плиток Жила/
   Резонанс/Эхо/Разлом внутри Комнаты можно на этом проходе сделать
   одним черновым фиксированным шаблоном через
   `SegmentTemplateCatalog`/`SegmentGenerationController` (не 30
   шаблонов — это контент-объём Спринта 18, здесь нужен один рабочий
   для критерия приёмки ниже).

### 5. Debug-визуал — обязательное условие приёмки

`DebugVisuals.TileDebugColor` уже частично готов (сигнатура опасности,
Спринт 12) — добавь цвета для `BossRoomTileKind.Vein`/`Resonance`/
`Rift`/`Echo` и входа в Комнату (`Tile.IsBoss`), по аналогии с
существующими цветами ловушек. Без этого критерий приёмки ниже
физически не проверить.

## Проверка

   плюс существующие (Resonance/Rift) не должны были сломаться.
2. Unity Test Runner на чистой пересборке целиком — это не должно
   задеть ничего вне `BossRoom`/`Core.BossRoomTileKind`/интеграционных
   точек.

   (Эхо после Резонансов и Эхо до Резонансов), чтобы визуально
   подтвердить критерий приёмки.
