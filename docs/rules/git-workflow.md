# Git-процесс

- НИКОГДА не пушить напрямую в master/main.
- Для любой задачи: агент сам создаёт новую ветку, коммитит изменения, тестирует, запушивает ветку и открывает Pull Request через `gh pr create`.
- Мерж PR делает только пользователь вручную на GitHub.
- НЕ добавлять в конец описания PR или коммитов пометку "Generated with Claude Code",
  "Co-Authored-By: Claude..." или любую другую атрибуцию инструменту/модели — ни в
  коммитах, ни в описаниях PR. Никогда, без исключений (прямое указание владельца
  продукта, 2026-08-18 — это правило уже было в файле раньше и всё равно нарушалось,
  проверять перед каждым коммитом/PR, а не полагаться на память).

## Коммитить сразу, не ждать одобрения

Агент **всегда** коммитит результат работы в свою ветку по ходу дела, не дожидаясь
одобрения владельца продукта. Незакоммиченное рабочее дерево в конце сессии —
недопустимо, даже если задача явно требует «дождись моего OK, потом коммить».

- Владелец продукта контролирует не факт коммита, а **мерж**: правило «не пушить
  и не мержить в `main` без одобрения» защищает `main`, а не рабочую ветку. Коммит
  в собственную ветку безопасен всегда и ничего не решает за владельца — решение
  остаётся за ним на этапе ревью PR.
- Новые файлы добавлять в индекс сразу (`git add`, включая новые/untracked), не
  оставлять их лежать неотслеживаемыми. `git stash` без `-u` не сохраняет
  untracked-файлы вообще, а `git stash show -p` не показывает даже то, что стеш
  сохранил с `-u` (untracked-часть — отдельное дерево, не входит в обычный diff) —
  полагаться на стеш как на способ временно избежать коммита не надо в принципе.
- Если работа не закончена — коммит с пометкой `wip:`/`Draft` в своей ветке, а не
  оставленное рабочее дерево, которое переживёт только до следующего `git
  checkout`.

**Почему это здесь**: в августе 2026 интеграция арта (`TileArtKind`,
`TileArtKindResolver`, `TileArtCatalog`, `ArtIntegrationSetup.cs`) была полностью
готова и проверена на устройстве, но агент оставил её незакоммиченной в ожидании
явного «ОК» на коммит. Рабочее дерево смыло переключением веток; результат
пролежал скрытым в untracked-части `git stash` больше недели, отрезанный от
`main`, который тем временем уехал на HUD/экономику/`RunBootstrap` — ветка чуть
не была признана «проще переписать с нуля». Правило без объяснения причины
рано или поздно снова превращается в «жду одобрения перед коммитом» — сама
причина должна остаться в файле, не только вывод.

## Конфликты docs/wiki/changelog.md

Все ветки дописывают новые секции в конец одного файла — это структурно
провоцирует конфликты между параллельными PR. Пока файл не разбит на
отдельные записи (см. ниже), при резолве конфликта changelog.md агент обязан:

1. Перед тем как писать резолв-текст, получить **актуальное** содержимое
   `main` через `web_fetch` по `raw.githubusercontent.com/.../main/docs/wiki/changelog.md`
   — не доверять локальному `origin/main` в песочнице: сети до GitHub из
   sandbox нет, локальный ref может быть устаревшим на много коммитов.
2. Не считать конфликт двусторонним «наша vs их последняя секция» — сверить,
   не пропала ли часть истории на одной из сторон (проверить количество `##`
   заголовков, при подозрении на потерю — сверить код соответствующих файлов
   через `web_fetch`, т.к. текст changelog.md может быть отредактирован в GitHub
   web-UI отдельно от реального мержа кода).
3. Резолв — это **объединение** обеих версий (все секции обеих сторон,
   в хронологическом порядке по факту выполнения работы), никогда не замена
   одной секции на другую и не отбрасывание существующей истории.
4. Отдавать пользователю резолв только как содержимое для вставки в
   **встроенный конфликт-редактор PR** (github.com/.../pull/N/conflicts) —
   никогда не как инструкцию редактировать `changelog.md` напрямую на ветке
   `main` в обход PR (такое прямое редактирование — вероятная причина, по
   которой история однажды уже терялась).

Если конфликты продолжат повторяться регулярно — рассмотреть переход на
паттерн «один файл — одна запись» (`docs/wiki/changelog/<issue-or-slug>.md`),
при котором параллельные ветки физически не могут задеть один и тот же файл.

## Сборка и проверка спринта перед мержем: интеграционная ветка

Спринт обычно состоит из нескольких задач, каждая — в своей ветке и со своим
PR (см. правило выше). Владелец продукта проверяет фиксы на устройстве
**до** мержа, и хочет видеть весь спринт целиком одной сборкой APK, а не
ставить и переустанавливать по одному PR — при этом мерж каждой задачи
остаётся отдельным решением (что-то может не пройти проверку, пока
остальное уже готово).

Решение — одноразовая интеграционная ветка, а не мерж всего спринта в одну
рабочую ветку с самого начала:

1. Все задачи спринта по-прежнему реализуются в отдельных ветках от `main`
   (или друг от друга, если есть реальная зависимость по коду — см.
   ниже) и открываются как самостоятельные PR.
2. Когда нужно собрать APK для совместной проверки — создать отдельную
   ветку от `main` с именем `integration/sprintNN<буква>-testing` и
   последовательно смержить в неё все актуальные PR-ветки спринта
   (`git merge --no-edit origin/<branch>` по очереди).
3. Конфликты (чаще всего — `docs/wiki/changelog.md`/`traps.md` и другие
   файлы, куда параллельные ветки дописывают в конец) резолвятся
   объединением обеих версий, не заменой одной другой.
4. Из интеграционной ветки собирается APK, ставится на устройство,
   владелец тестирует все фиксы спринта вместе.
5. Эта ветка **никогда не становится PR и никогда не мержится** — она
   существует только для сборки/теста. По итогам проверки владелец решает,
   какие из отдельных PR мержить и в каком порядке; ветку можно запушить в
   `origin` как бэкап, явно предупредив, что она не для мержа, или просто
   удалить локально после того, как решение принято.

Почему не одна общая ветка на весь спринт с самого начала: тогда нельзя
смержить прошедшую проверку часть спринта отдельно от не прошедшей, один
большой diff тяжелее вязать с конкретным багом, если он всплывёт после
мержа, и откат одной правки без отката остальных перестаёт быть
тривиальным. Ветка-на-задачу + временная интеграционная ветка для теста
сохраняют оба свойства: спринт виден целиком до мержа, а мерж остаётся
гранулярным.

Если у новой задачи спринта есть прямая кодовая зависимость от ещё не
смерженной ветки другой задачи (нужен метод/API, который существует только
там) — эта задача branch'ится не от `main`, а от той ветки
(`git checkout -b new-branch origin/sibling-branch`), и её PR открывается с
`--base <sibling-branch>`, а не `main`, с явной пометкой в теле PR о
порядке мержа. Из независимости веток друг от друга (шаг 1) это не
исключение, а осознанный выбор — когда зависимость реальная, притворяться,
что её нет, значит ломать сборку интеграционной ветки на шаге 2.
