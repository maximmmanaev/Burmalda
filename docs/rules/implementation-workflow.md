# Порядок реализации задачи

Перед тем как писать любой код по issue, агент обязан пройти три шага по порядку —
пропускать или менять местами нельзя.

## 1. Изучить архитектуру вертикально

Проследить путь, который затрагивает ИМЕННО задача, сверху вниз: от точки входа
(ввод/событие/вызов извне) через промежуточные слои до данных, которые меняются
в итоге. Для Unity/C#-кода это обычно: `MonoBehaviour`/точка входа →
логика/сервис-классы → данные (`Core`). Понять, какие существующие классы и
асинхронные сборки (`asmdef`) уже покрывают часть этого пути, а какие предстоит
добавить. Границы — конкретный затрагиваемый путь, не вся система вокруг него
(см. [token-economy.md](token-economy.md) про то, как читать код точечно).

## 2. Изучить архитектуру горизонтально

Найти ОДИН наиболее похожий по роли модуль на том же уровне
(`Assets/Scripts/<Другая система>/`) как образец — не обходить несколько
подряд "для надёжности". Цель образца — соглашения по асимметрии
`asmdef`+`Tests`, именованию, DI/конструкторам, уже устоявшиеся в проекте: не
изобретать новый паттерн там, где уже есть согласованный, и не дублировать
логику, которая уже есть в `Core` или смежной системе. Если один образец не
снимает вопрос — можно посмотреть второй, но не больше.

**Стоп после 8 файлов.** Если шаги 1–2 вместе дали прочитать 8 файлов, а
ясности по подходу всё ещё нет — не продолжать чтение по инерции:
остановиться и описать открытый вопрос (что неясно, что уже проверено).

## 3. Тест → код

Только после шагов 1–2:

1. Сначала написать тест(ы) Unity Test Framework под критерии приёмки issue —
   тест должен падать (не компилироваться/быть красным), пока кода ещё нет.
2. Затем написать минимальный код, который делает тест зелёным.
3. При необходимости — рефакторинг с сохранением зелёных тестов.

Код без предшествующего теста (кроме случаев, явно не тестируемых без сцены —
см. `docs/rules/ci.md`) писать нельзя.

Во время итераций (между красным и зелёным) гонять только целевые
тест(ы) по задаче, не весь EditMode-прогон. Полный EditMode-прогон —
один раз, перед открытием PR. В вывод/контекст брать только упавшие
тесты и итоговую строку прогона (сколько прошло/упало), не весь лог.

## Баг: гипотеза и лимит попыток

Правка бага начинается с красного теста-воспроизведения (частный случай
шага 3 выше, не исключение из него). Гипотезу о причине из текста issue
сначала проверить по коду — не принимать на веру чужую формулировку.

После двух неудачных попыток исправить одну и ту же ошибку —
остановиться, не пробовать третий вариант вслепую: написать журнал
попыток (что пробовал, почему не сработало) в комментарий к issue.
