# C#-глоссарий терминологии

Соответствие терминов из [docs/rules/terminology.md](../rules/terminology.md) именам
классов, полей и enum-значений в Unity/C#-коде. Единственный актуальный источник —
[PRD v8](../raw/BURMALDA_PRD_v8.md) (v4–v7 устарели). PRD v8 оформлен как
дельта к v7: разделы 5–10, 13–14, 18–19, 27–28 обновлены/добавлены (Комната
Босса полностью заменяет Боссов v6/v7, оси артефактов заменяют Созвучия,
Реликвии получают тиры и Вес, Отклик Шахты — новый раздел 28), разделы
20–26 сохраняются из v7 без изменений (кроме отменённых пунктов — см. §27
PRD v8), остальные — из v6/v4. Стиль — Unity/C# (PascalCase для
публичных членов, см. [docs/rules/code-style.md](../rules/code-style.md)).

**Термины, устаревшие с PRD v8** (удаляются или помечены как не
переиспользуемые — см. [Roadmap, «Миграция кода»](roadmap.md#миграция-кода-боссы-v7--комната-босса-v8)):
`Boss.RequiredEnergy`, `Boss.Resolve`, `Boss.OverflowToCoinsRate`/
`OverflowRelicBonusMultiplier` (Перелив энергии — `ManaOverflow` по смыслу),
`BossSeal` (Печати Боссов, не были реализованы), `Altar.ManaToBossIndicator`,
`Artifacts.ArtifactTag`/`ResonanceType`/`ResonanceCalculator` (Созвучия).
Запись `Resonance` в этом глоссарии ниже означает **только** плиту-Резонанс
(`BossRoomTileKind.Resonance`) и ось-Резонанс (`ArtifactAxis.Resonance`) —
значение «Созвучие» (`ResonanceType` из PRD v7 §6.1) отменено и конфликтует
с этими двумя, поэтому не используется.

Список не придумывает сущностей сверх того, что описано в PRD — только даёт им
технические идентификаторы.

## Core-движение — тоннель, сетка, grid-trace (раздел 4.1)

**Ввод переработан под PRD v8 §4.1 (issue #157): непрерывная протяжка
отменена**, вместо неё дискретный шаг с подтверждением — удержание пальца
на соседней плите примеривает её (`GridTraceInputController.PreviewTarget`,
трейл НЕ двигается), ведение без отрыва переносит примеривание, отпускание
фиксирует шаг и блокирует ввод на `StepDurationSeconds` (0.15–0.5с),
отпускание вне валидной соседней плиты — отмена без шага. Камера
обновляется только между шагами — часть механики, не оптимизация (см.
`TunnelCameraController.IsPressed`-гейт ниже). Распад (Decay, см. ниже)
тикает и во время примеривания, и во время анимации шага — раздумье платит
временем, пауз нет. Владелец выбрал эту схему после спайка (issue #157,
изначально сравнивалось две альтернативы, схема B — "невидимый джойстик" —
отброшена: серийные шаги при удержании превращали игру в автобег).

Нет автоскролла камеры — давление идёт от распада плит позади, не от
таймера. Идентификаторы ниже реализуют саму сетку и приём/валидацию
трейс-хода; тип плиты (ловушка/валюта/артефакт) — предмет других систем/
спринтов и добавляется поверх `GridCoordinate` без изменения этого раздела.

Тап по экрану разрешается в координату плиты через `Physics.Raycast` против
РЕАЛЬНЫХ коллайдеров плиток (`GridTraceInputController.ResolveTappedTile`),
не абстрактную математическую плоскость пола (2026-08-14, реальный баг, не
гипотеза: раньше `Plane(Vector3.up, Vector3.zero)` давала какую-то мировую
точку для ЛЮБОГО тапа, включая пустой пол за пределами раскрытой сетки —
тап мимо всей видимой геометрии всё равно двигал камеру/трейл). Координата
читается прямо с компонента `TileVisualMarker` попавшего коллайдера, не
пересчитывается обратно из точки удара — обратный пересчёт был бы той же
самой ошибкой. `null`, если луч ни во что не попал — вызывающий код тихо
ничего не делает. `GridTraceTrail.CanAdvanceTo`/`TryAdvanceTo` не менялись.

`TunnelGrid.MaterializedTiles` — снимок уже материализованных плит на
текущий момент, прямой доступ к состоянию, а не только через событие
`TileMaterialized` (идемпотентное — стреляет один раз за координату
навсегда). Нужен, чтобы догнать пропущенные события: порядок `Update()`
между независимыми MonoBehaviour-компонентами Unity не гарантирует — если
`TunnelObstacleController` (материализует `TunnelGridReveal` рядов вперёд
игрока) успевает отработать РАНЬШЕ, чем `Burmalda.DebugVisuals.TunnelDebugVisual`
подписался на `TileMaterialized`, те события улетают в пустоту без второго
шанса, и плиты остаются без GameObject НАВСЕГДА (реальный баг на
устройстве, 2026-08-14: "одинокая плитка" вместо всей раскрытой вперёд
сетки — только стартовая плита получала GameObject). Фикс — точечный:
конструктор `TunnelDebugVisual` теперь бэкфиллит ВСЕ уже материализованные
плиты грида (`MaterializedTiles`), не только пройденные (`GridTraceTrail.Path`).
Сам race по порядку `Update()` не устранён (это отдельная, более общая
архитектурная тема, тот же класс проблем, что и `RunStarted`/`Awake`/
`OnEnable`, см. `TunnelCameraController`).

## Decay — распад плит трейла (разделы 4.1, 16)

Плиты позади игрока распадаются и разрушаются со временем — источник
постоянного давления вместо таймера на прохождение (раздел 4.1). Портировано
из `updateDecay()`/`tryAct()` в `legacy/burmolda_demo.html` (раздел 16:
перенос 2D top-down прототипа в 3D) без изменения констант тайминга; состояние
распада хранится прямо на `Tile` (см. выше), само тиканье — в `TrailDecaySystem`.

## Камера тоннеля (раздел 16)

3D-камера от третьего лица следует за трейлом сверху-сзади вместо 2D-скролла
прототипа (раздел 16: перенос HTML top-down прототипа в Unity). Портировано
из camera-логики `legacy/burmolda_demo.html` (`cameraRow`/`cameraTargetRow`,
`draw()`) — константа сглаживания и офсет отставания по ряду перенесены
буквально; высота камеры над игроком — новое значение для 3D, аналога в
2D-прототипе нет (см. issue #8, скоуп увеличен с 2D до 3D третьего лица).
Персонаж не отображается — камера следует за
`GridTraceTrail.CurrentPosition` через `WorldGridProjection.ToWorldPosition`.

`TunnelCameraFollow.HeightOffset`/`PitchDegrees`/`IntroPitchDegrees`/
`IntroHeightOffsetZ` — публично изменяемые свойства (не только
конструкторские параметры): двигать `Transform` `TunnelCameraController`
напрямую в Scene view/инспекторе нельзя, он каждый кадр перезаписывается
результатом Follow — вместо этого меняются соответствующие поля в
инспекторе `TunnelCameraController`, которые прокидываются в `Follow`
каждый кадр и применяются вживую, без рестарта забега.

**Top-down интро выключено целиком (2026-08-14, прямой запрос владельца
продукта)** — камера стоит на устоявшихся `PitchDegrees`/`HeightOffset.Z` с
первого кадра, без какой-либо анимации/перехода. История для контекста (обе
предыдущие архитектуры уже убраны, не искать их в текущем коде):
1. Изначально — row-based интерполяция по `ComputeCatchUpScale(playerRow)`
   (`caughtUpDistance/TrailingRowsBehindPlayer`) — источник серии регрессий
   на реальном устройстве (плита уходит за край экрана при частичном
   продвижении).
2. Заменена на явный тап-триггер: `ConfirmRun()` (тап по собственной
   текущей позиции игрока, см. `GridTraceInputController.RunConfirmed`)
   запускает короткий time-based твин (`TweenDurationSeconds=0.35с`,
   `AdvanceIntroTween`, easing `EaseOutCubic`) от `IntroPitchDegrees`/
   `IntroHeightOffsetZ` к устоявшимся значениям.
3. Твин полностью отключён по прямому запросу (приватный
   `ComputeIntroTweenProgress01()` захардкожен на `1` — прогресс твина
   всегда "уже завершён"): `IntroPitchDegrees`/`IntroHeightOffsetZ`/
   `DefaultIntroPitchDegrees`/`DefaultIntroHeightOffsetZ` остались
   публичными свойствами/константами (не удалены — история/потенциальный
   будущий возврат), но их значение больше никак не проявляется визуально.

`ConfirmRun()`/`AdvanceIntroTween()` при этом НЕ удалены и продолжают
работать как бухгалтерия (elapsed-time твина) — `TunnelCameraController`
по-прежнему вызывает `AdvanceIntroTween(Time.deltaTime)` каждый кадр, и это
не no-op: `AdvanceIntroTween` — единственный путь, которым `CurrentPosition`
мог оказаться захардкожен в `TargetPosition` БЕЗ сглаживания `Tick()`, даже
когда пункт 3 выше уже выключил видимую часть твина. Реальный баг (2026-08-14,
не гипотеза, подтверждён логами на устройстве): непрерывный жест (тап по
своей же плите → сразу свайп вперёд, без отрыва пальца) успевал продвинуть
игрока РЕАЛЬНО внутри 0.35-секундного окна после `ConfirmRun()` —
`TargetPosition` уже отражала новый ряд (`OnPositionChanged`), а безусловный
хард-синк телепортировал камеру на него без `SmoothingFactor`, что читалось
как рывок на несколько клеток около 3–4 хода. Фикс: `ConfirmRun()` запоминает
`_confirmRunPlayerPosition`; `AdvanceIntroTween` завершает твин немедленно
(без хард-синка на этом кадре), если `GridTraceTrail.CurrentPosition`
отличается от снапшота — дальше `CurrentPosition` едет к цели только через
обычный `Tick()`, как любое другое продвижение.

`HeightOffset.Z` (дефолт `0`, было `2`) — восстанавливает дистанцию
камера-игрок в исходные `TrailingRowsBehindPlayer` тайлов (`3`): дистанция
считается как `TrailingRowsBehindPlayer*tileSize − HeightOffset.Z`, а
`TrailingRowsBehindPlayer` тихо поменяли `5→3` отдельной правкой без
пересчёта `Z` (`5−2=3` стало `3−2=1` — плитка прижалась к нижнему краю
кадра, `viewport.y` 0.324→0.065, измерено `WorldToViewportPoint` на
реальном устройстве, не на глаз). `Z=0` не своё отдельное значение, а
компенсация чужого рассинхрона (`3−0=3`). Ряд 0 (playerRow=0) и устоявшееся
состояние теперь буквально одно и то же число — дистанция камера-игрок не
зависит от `Row` (без клампа трейлинг-ряда к 0, см. ниже).

Трейлинг-ряд БЕЗ клампа к 0 (убран, было `Math.Max(0, playerRow -
TrailingRowsBehindPlayer)`) — на 2D top-down прототипе клампинг был не
критичен, а в 3D-геометрии этого проекта именно он схлопывал дистанцию
камера-игрок на первых `TrailingRowsBehindPlayer` рядах (камера
оказывалась ВПЕРЕДИ игрока по Z на `row=0`, "поле не попадает в кадр").

`TunnelCameraFollow.SnapToTarget()` — мгновенный (без сглаживания) снап
`CurrentPosition` к `TargetPosition`. **Больше не вызывается на каждый
новый тап** (2026-08-14, реальный баг на устройстве, не гипотеза): раньше
`TunnelCameraController.HandlePressStarted` вызывал его на каждый переход
"не прижат"→"прижат" — при заметном разрыве `Current`/`Target`
(`SmoothingFactor=0.01` очень медленный) мгновенный снап читался как рывок
камеры на несколько клеток. Заменён на `ResetManualForwardOffset()` — тот
же сброс накопленного эдж-скролла (`NudgeForward`), но БЕЗ снапа позиции;
обычное продвижение теперь всегда идёт только через `Tick()`/
`SmoothingFactor`, без исключений на новый тап. `SnapToTarget()` оставлен
публичным (не удалён) — для места, где мгновенный снап реально нужен
(например, самый первый старт забега, если когда-нибудь понадобится), но
такого места сейчас нет.

`TunnelCameraFollow.CurrentPitchDegrees` — то же число, что в
`TargetRotation.eulerAngles.x`, но напрямую как градусы, без раскрытия
кватерниона. Нужно `TunnelCameraController`, который пересчитывает
горизонтальный FOV КАЖДЫЙ кадр (не только на (пере)сборке следования) от
этого живого pitch — исторически (до отключения интро выше) FOV,
откалиброванный один раз под устоявшийся `PitchDegrees`, не годился для
геометрии top-down интро; сейчас pitch константен, но пересчёт остался —
дёшево, и не требует отдельного условия на состояние твина.

`TunnelCameraFraming.ComputeDesiredHorizontalFovDegrees` берёт депт до
опорного ряда ВДОЛЬ ОСИ ВЗГЛЯДА камеры (`cameraHeight*sin(pitch) +
groundDistanceToRow*cos(pitch)`), не по прямой — обязательное условие
того, чтобы `Pitch Degrees` был по-настоящему тюнящимся полем. Хотя интро
выключено, `groundDistanceToRow`
(`ComputeSteadyStateGroundDistanceToReferenceRow`) и до этого зависел
только от констант (`HeightOffset.Z`/`TileSize`/`TrailingRowsBehindPlayer`),
не от текущего ряда игрока — FOV не может "прыгать" по ходу забега (это
явно проверялось и опровергалось как причина отдельного репортнутого рывка
камеры — реальной причиной оказался хард-синк `AdvanceIntroTween` выше, не
FOV).

## Ловушки и рычаги (раздел 4.2)

**Скрытые ловушки (переработка PRD v8 §4.2, issue #163)**: яма и взрыв
(после активации триггером) больше не видны заранее — вместо точного типа
плита несёт общую сигнатуру опасности, для всех и всегда, без единого
Идола (`Core.TrapSignature.IsHiddenLethalTrap`). Точный тип (Идол Чутья) и
скрытая ценность под плитой (Идол Жадности) раскрываются только при
примеривании, через крючки `Movement.TrapInsight` — сейчас оба флага
всегда false (Идолы пока безымянные, см. `Artifacts.Idol`), владелец
продукта подключит реальную проверку, когда у Идолов появится конкретная
роль. **Лава и заблокированные плиты — вне этого правила**, видны как
раньше. Ловушка с таймингом (стрела/лезвие) тоже вне: до активации плита-
цель структурно неотличима от обычной (см. `TimedTrapSystem` ниже), а
активная фаза (`Tile.IsTimedTrapActive`) — реальная угроза прямо сейчас, не
предмет сокрытия.
